# 고객 보고서 피드백에서 Excel VBA 검산까지

2026년 11월 9일 한국 시간에 진행한 SlideFill 작업의 기록입니다. 프로젝트 제작자가 개발 방향을 정하고, 내장한 VBA 모듈을 Excel과 앱에서 모두 호출하자고 제안했으며, Excel에서 시험 파일을 각각 승인했습니다. Codex는 문헌 조사, 구현, 실험을 지원했습니다. [개발·검증 이력](development-history.ko.md)

## 깔끔한 슬라이드가 잘못된 숫자를 가릴 수 있다

프로젝트 소개에 대해 사람이 검토하지 않은 자동 생성 보고서를 고객에게 보낼 만큼 신뢰할 수 있느냐는 질문을 받았습니다. 제작자는 커밋 `13dfc27`에서 README 상단에 사람이 검토할 범위를 표시했습니다. 후속 피드백은 슬라이드가 깔끔하면 잘못된 숫자를 놓친 채 보내기 더 쉽다고 지적했습니다. 제작자는 이어 사람이 계산을 다시 확인하는 부담을 줄이도록 구현을 강화하자고 요청했습니다. 앱이 확인할 수 있는 단계와 보고서 작성자가 판단할 단계를 나누는 것이 출발점이었습니다.

첫 구현에서는 원본 선택, 계산, 저장한 PowerPoint 검사를 분리했습니다. 지원하는 입력은 정확한 유리수 중간값을 유지하고, 지원하는 수식 캐시와 의존성을 독립적으로 평가하며, 불일치나 불완전한 독립 검증이 감지되면 저장을 보류하도록 했습니다. 범위를 정한 Dafny 핵심에는 명시한 정수·반올림 계약을 적용했습니다. 원본 해석, 차트 데이터, 저장 슬라이드는 별도로 시험했습니다. 기능별 문서에서는 정확한 연산과 시트, 분모, 단위, 기간을 고르는 판단을 나눠 적었습니다. [수치 신뢰성](reliability-hardening.ko.md), [기능별 알고리즘](feature-algorithms.ko.md), [검증 설계](verification-design.ko.md)

## 살펴본 논문과 실험 설계

제작자의 요청으로 Liner Scholar에서 스프레드시트의 머리글·출처, 테스트 오라클과 메타모픽 테스트, 계약, 구현 간 수치 편차를 여섯 차례 검색했습니다. 두 논문은 관련 본문 발췌를 받아 확인했고, 세 편은 초록 수준에서 살폈습니다. *jContractor*와 *Metamorphic testing and beyond*는 본문 이용 가능으로 표시됐으나 두 가져오기 모두 실패했습니다. 아래에는 당시 참고한 근거 수준을 적었고, 링크는 이번 기록을 작성하며 확인한 논문 원문이나 저자 소속 기관의 기록입니다. [연구 방법과 근거 수준](research-methods.ko.md)

- **Robin Abraham·Martin Erwig, 2004년.** 본문 발췌에서 공간 배치를 이용한 머리글 추론이 단위 검사에 어떻게 쓰이는지 살폈습니다. 이를 참고해 비교 종류, 기간, 정확한 값을 모듈 사이에서 명시적으로 전달했습니다. 업무상 올바른 지표와 단위는 해당 자료를 보고 판단해야 합니다. [Header and Unit Inference for Spreadsheets Through Spatial Analyses](https://web.engr.oregonstate.edu/~erwig/papers/HeaderInf_VLHCC04.pdf)
- **Huai Liu 외, 2014년 권호.** 본문 발췌는 개별 정답을 일일이 쓰기 어려울 때 여러 실행 간에 성립해야 할 관계를 검사하는 방법을 다룹니다. 명시한 전제 안에서 동등한 수치 표기, 양수 배율, 변화 방향의 보존을 검사하고 구체적인 반례도 추가했습니다. [How Effectively Does Metamorphic Testing Alleviate the Oracle Problem?](https://nottingham-repository.worktribe.com/output/720879/how-effectively-does-metamorphic-testing-alleviate-the-oracle-problem)
- **Earl T. Barr 외, 2015년.** 초록에서는 명세, 계약, 메타모픽 테스트, 사람의 업무 지식을 기대 동작의 근거로 다룹니다. 저희는 정확한 수학 기준, 저장 결과에 대한 독립 검사, Office 관측을 분리하고 각 결과가 일치한 범위를 기록했습니다. [The Oracle Problem in Software Testing: A Survey](https://discovery.ucl.ac.uk/id/eprint/1471263/)
- **M. Moein Almasi 외, 2018년.** 두 금융 앱에서 스프레드시트 계산을 Java로 옮기며 생기는 편차를 조사한 연구의 초록을 봤습니다. 저희 합성 사례에는 서로 인접한 큰 정수, 긴 소수, 아주 작은 변화, 큰 수의 상쇄를 넣었습니다. [Search-Based Detection of Deviation Failures in the Migration of Legacy Spreadsheet Applications](https://philmcminn.com/publications/almasi2018.pdf)
- **Tsong Yueh Chen 외, 2018년.** 초록에서는 여러 입력과 결과가 만족해야 하는 관계를 이용한 테스트 생성·검증과 적절한 관계를 고르는 어려움을 살폈습니다. 저희는 각 관계가 성립할 조건을 적고, 잘못된 통과와 올바른 결과의 거절을 모두 시험했습니다. [Metamorphic Testing: A Review of Challenges and Opportunities](https://hub.hku.hk/handle/10722/254895)

이 과정에서 선택 통찰 문장의 숫자 표기를 정확히 구분하고, 파일 간 비교에 정확한 상대 변화값을 전달하고, 내용 바꾸기 캔버스에 누락 구간과 양·음수의 영 기준선을 보존하도록 개선했습니다. 논문은 각자의 방법과 시스템을 다뤘고, SlideFill에 적용한 선택은 표적 회귀 검사와 실제 저장 결과로 따로 확인했습니다. [계산에서 문장까지 정보 보존](reliability-hardening.ko.md#계산에서-문장까지-정보-보존)

## 실제 Excel과 PowerPoint로 본 결과

제작자는 실제 Excel과 앱의 내용 바꾸기 캔버스를 열고 눈으로 대조하자고 요청했습니다. Excel 16.0 빌드 20326에서 `AVERAGE` 수식 여섯 개를 다시 계산하고 차트 이미지 세 개를 내보냈습니다. 실제 PowerPoint에서는 영어·한국어 보고서 슬라이드 여섯 장을 내보냈습니다. 검토한 이미지에서 의도한 평균, 영 기준선에서 양·음으로 갈라지는 막대, 누락된 값의 빈 구간을 확인했습니다. 실제 Tk 캔버스에도 합성 통합 문서를 정상 경로로 읽어 정확한 값 여섯 개를 넣었습니다. 이 실행에서는 화면 캡처가 시간 초과됐고 접근성 정보도 부족해 전체 창의 배치와 클릭 흐름 확인은 보류했습니다. Office에서 직접 내보낸 이미지는 선택한 차트와 슬라이드의 렌더링 근거입니다. [환경 시험 범위](testing-alternatives.ko.md)

## 제작자가 제안한 VBA 내장

제작자는 서로 다른 환경에서 억지로 동작을 맞추려는 데서 일부 차이가 생긴다고 봤습니다. 같은 연산을 VBA 모듈로 작성해 내장하고, Excel 안에서 실행한 값과 앱이 호출한 값을 먼저 비교하자고 제안했습니다. 기존 Python 코드, 수식, 수학 알고리즘도 유지하자는 조건이 있었습니다. 이 제안에 따라 세 경로를 비교했습니다.

1. Excel 시트의 VBA 사용자 정의 함수가 직접 작성한 `SFCalc` 모듈을 호출합니다.
2. 앱 쪽 비교 실행기가 Excel `Application.Run`으로 같은 모듈을 호출합니다.
3. Python은 기존 정확한 산술과 반올림 규칙으로 지정된 연산을 계산합니다.

두 VBA 경로는 같은 구현과 Excel 런타임을 공유하므로 일치는 앱 경계를 넘나드는 입력과 결과의 전달을 검증합니다. Python은 프로젝트에 명시한 규칙에 따른 별도의 수학적 기준입니다. [직접 작성한 VBA 소스](../tools/vba/SlideFillOracle.bas), [Excel Application.Run](https://learn.microsoft.com/en-us/office/vba/api/excel.application.run)

## 실제 실행 전 발견한 문제

Excel이 VBA 프로젝트에 대한 프로그램 접근을 거부했습니다. 처음 차단된 실행에서는 입력 21개를 확인했으나 VBA를 실행한 사례는 0개였습니다. 제작자가 편집기의 파일 가져오기를 이용했고, 중복 모듈 때문에 `Ambiguous name detected: SFCalc` 오류가 발생하자 중복본을 지운 뒤 모듈이 하나인 통합 문서를 저장했습니다. 다른 준비 검사에서는 `Value2`를 이용한 일괄 복사로 숫자처럼 보이는 문자열이 숫자로 바뀐 것을 찾았습니다. 수정한 시험 파일은 원본과 VBA 바이너리를 보존했고, 실행 전에 실제 입력 형식과 수치의 Double 비트를 확인했습니다. 기존 Office 정책에서 시험 파일만 개별 승인했습니다. [VBA 준비와 재현 절차](../tools/vba/README.ko.md), [Office 개발자 보안 문서](https://learn.microsoft.com/en-us/office/vba/library-reference/concepts/security-notes-for-microsoft-office-solution-developers)

## 실험 결과

수정 뒤 데스크톱 Excel 16.0 빌드 20326에서 두 경로 모두 **21개 중 21개**를 실행했습니다. 시트와 앱 호출은 전부 일치했고, 수치 16개는 Double 비트가 같았고 오류 5개는 오류 코드가 같았습니다. Python과 VBA는 Python 값에 가장 가까운 Double 또는 기대 오류 코드를 기준으로 **21개 중 17개**가 일치했습니다. 나머지 네 개는 차이로 기록했습니다. [전체 비교와 연산 계약](../tools/vba/README.ko.md#실제-실행-결과)

| 합성 사례 | 두 VBA 경로의 값 | Python의 정확한 값 |
|---|---:|---:|
| Double 누적으로 `0.1 + 0.2` | `0.30000000000000004` | `3/10` |
| `10^16 + 1 − 10^16` | `0` | `1` |
| `100`에서 `100.00000001`로의 상대 변화 | `9.9999937219763522e-11` | `1/10000000000` |
| VBA `Round` 시험에서 `2.5`를 정수로 반올림 | `2` | 절반에서 0과 멀어지는 규칙으로 `3` |

큰 정수 사례에서는 정확한 입력 `9007199254740993`을 두 VBA 경로 모두 `9007199254740992`로 반환했습니다. Double 기준에서는 일치했지만 정확한 값과는 1의 차이가 있었습니다. 반올림 행은 정확히 절반일 때 짝수 쪽을 택하는 VBA `Round`를 따로 호출한 진단입니다. [비교 계약](../tools/vba/README.ko.md#고정한-연산-계약), [Microsoft VBA Round 문서](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/round-function)

## 실험을 앱 기능에 반영한 방식

21개 사례를 실행한 뒤 선택 기능으로 **Excel VBA 검산**을 넣었습니다. SlideFill은 Python으로 보고서 값을 계산하고, 지원하는 단일 열의 합계·평균·개수를 검증된 표와 차트에서 따로 대조합니다. 결과는 정확한 일치, Double로 변환했을 때의 일치, 차이로 구분합니다. 설치된 데스크톱 Excel의 별도 인스턴스에서 앱 자체의 해시 확인된 매크로 통합 문서만 읽기 전용으로 열고, 기존 매크로 정책을 따릅니다. 앱에 포함되는 것은 프로젝트 자체의 VBA 모듈이고 실행 환경은 설치된 Excel이 제공합니다. [사용법](../README.ko.md#excel-vba로-검산), [Excel AutomationSecurity](https://learn.microsoft.com/en-us/office/vba/api/excel.application.automationsecurity)

이후 EXE에서 추출한 깨끗한 통합 문서는 격리한 복사본과 EXE 옆 경로에서 모두 Office 정책에 의해 처음에는 실행이 막혔습니다. 제작자가 그 통합 문서에 콘텐츠 사용을 누르고 저장하지 않고 닫자, 패키지의 실행기와 통합 문서가 읽기 전용으로 **일곱 개 기대값을 모두 반환**했고 파일 해시가 일치했습니다. 합계·평균·개수, 직전 일곱 값의 평균, 세 가지 상대 변화가 대상이었습니다. 이 실행에서는 화면 캡처 실패로 패키지의 실행기를 직접 호출했고, 검산 결과 창은 별도의 소스 GUI 시험에서 확인했습니다. [VBA 대조 절차](../tools/vba/README.ko.md)

## 수치와 문장을 확인하는 사용 흐름

제작자는 사용 흐름을 안내하고 통찰 문장 제안도 더 정확하게 만들자고 요청했습니다. 도움말은 입력과 미리보기에서 선택 검산, 통찰 검토, 저장으로 이어집니다. 통찰 검사는 비교 기간과 증감 방향을 확인하고 후보에 사용한 근거를 보여 줍니다. 한국어·영어 재시험에서 의도적으로 틀린 문장 여덟 개를 걸러냈고 맞는 문장 네 개를 유지했습니다. 패키지의 실제 모델이 만든 한국어 후보 여섯 개도 합성 데이터의 해당 VBA 비교와 맞았습니다. 현재값 `99`를 기준으로 `90` 대비 `+10.0%`, `110` 대비 `−10.0%`, 직전 일곱 값의 평균 `101` 대비 `−2.0%`였습니다. 이 결과는 해당 수치와 방향, 비교 기준에 관한 근거입니다. [사용 흐름](../README.ko.md#사용법), [검증 범위](verification.ko.md)

**참조 추천**을 다시 살피며 조건 선택 문제도 두 건 찾았습니다. **모든 행**을 골라도 기본 국내선 필터가 돌아와 김포의 전체 합계 `160` 대신 `10`이 나왔습니다. 다른 사례는 조건을 세 개 적용하고 두 개만 표시해 다시 계산하면 환자 조건이 빠지면서 `30`이 `330`이 됐습니다. 조건 생략과 명시적으로 비운 선택을 구분하고, 적용된 조건을 모두 표시하며, 조건이 완성되기 전에는 이전 결과를 복사하거나 적용할 수 없게 했습니다. 영어·한국어 GUI로 세 번째 조건을 유지하고 해제하는 경우, 조건이 다섯 개인 경우의 스크롤을 시험했습니다. 직접 선택한 `330`이 저장한 PowerPoint에 들어간 것도 확인했습니다. [기존 계산 회귀 검사](../test_core.py), [GUI 회귀 검사](../tools/gui_check.py)

실험 결과가 뒷받침하는 범위는 명시한 시험 파일, 계산, 실행 환경입니다. 고객에게 보낼 보고서는 선택한 지표와 기간, 원본의 최신성, 단위, 문장, 최종 배치를 함께 확인합니다. 처음의 피드백을 실제로 점검하려면 이런 판단이 수치 옆에 드러나야 합니다. [지원 배치와 한계](limits.ko.md)
